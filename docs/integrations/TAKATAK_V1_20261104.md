# CUBARESORT → TAKATAK V1 integration discovery

Signed Codex · 2026-11-04. Read-only discovery; no V1 code, credentials or production settings changed.

## Verified current contracts

- `takatak-v1/docs/ON2GO_MASTER_API.md`: ON2GO customer and Food Hub merchant scopes have separate 32+ character server credentials; OTP send/verify, identity resolution, source-scoped events. Food Hub adds merchant resolution and entitlements.
- ON2GO launch/exchange bridge: single-use 90-second code, server-only service token, 10-minute identity grant, live identity introspection. This is ON2GO-specific, not an authorized CUBARESORT session route.
- `docs/QMAPS_LISTINGS_REVIEWS_SYNC.md`: QMAPS pushes HMAC-signed listing/review events into V1. V1 does not call QMAPS. A unique admin-approved business/workspace mapping controls tenant access. No sibling-to-sibling calls.
- `docs/CUBAFOOD_MASTER_API_CONTRACT.md`: distinct CUBAFOOD operational app, opaque participant/partner/lead events; explicitly contract-only with no live route. Do not confuse it with Food Hub delivery or register CUBARESORT as cubafood.

## Required CUBARESORT registration

Add a dedicated cubaresort scope and launch/exchange/introspect adapter on V1 after source/workspace/entitlement registration is confirmed. Never send a Food Hub or ON2GO source value to impersonate those applications. Keep CUBARESORT's service key server-side and separate per environment. Store only opaque identity/tenant references in operational bookings; V1 remains identity authority.

For merchant food/driver/activity operations use a durable CUBARESORT transactional store and source-specific V1 events, not static browser storage as an order database. QMAPS publication must pass through the authorized V1 route, not directly into its database.

## Intended reservation lifecycle

1. Verified identity + tenant from server-side V1 session introspection.
2. Draft itinerary: travel, lodging, transport, activities, connectivity, food.
3. Provider quotes with currency, total fees, expiry and cancellation policy.
4. Explicit customer acceptance; create provider holds where supported.
5. Authorize payment only through an approved payment provider; never in browser code.
6. Confirm each component using provider receipt; handle partial failures with cancellation/compensation and a reconciliation queue.
7. Emit minimized idempotent V1 events; expose only that identity/tenant's reservations.
8. Food fulfilment includes merchant acceptance, internal driver assignment, pickup/delivery evidence and incident handling. Never mark dispatched/delivered from an AI response.

## Backend access handoff

Needed: real backend URL, official API documentation or sandbox, dedicated CUBARESORT test identity/source mapping, scoped server credential supplied through deployment secrets, supported supplier contract IDs and test cases. No owner password, shared browser session or admin cookie goes into client JavaScript. A web login session is not an API authorization contract.
